\begin{abstract}
Image-based dietary assessment becomes useful only when visual detections are connected to reliable nutrition records and user-specific dietary context. This article presents an AI-based food recognition system with nutrition-aware recommendations for Indian meals. The system combines a You Only Look Once version 11 small (YOLO11s) detector, a 72-class curated Indian food dataset, a SQLite nutrition database derived primarily from Indian food-composition data, audited detector-to-database mappings, a FastAPI backend, a Next.js frontend, a deterministic macro-target engine, and a recommendation service that uses computed backend nutrition values rather than generating nutrient numbers. Five YOLO-format datasets were normalized into 48,693 exported image-label pairs across training, validation, and held-out test splits. Visual verification confirmed samples for all 72 classes and identified three annotation-level issues for later cleaning. The final detector achieved 0.847 precision, 0.807 recall, 0.830 mean average precision at 0.50 intersection-over-union (mAP@50), and 0.692 mAP@50:95 on validation, and 0.842 precision, 0.801 recall, 0.820 mAP@50, and 0.680 mAP@50:95 on the held-out test split. The nutrition layer contains 1,010 food records and 103 audited detector-to-database mappings, covering all 72 expanded classes. The prototype supports upload, detection overlays, per-100 g macro display, serving adjustment, daily macro tracking, health-condition-aware macro targets, and concise dietary recommendations. The results show that credible regional food-recognition systems require not only accurate visual models, but also reproducible label normalization, auditable nutrition provenance, conservative mapping, and clear separation between nutrition calculation and generated advice.
\end{abstract}

\section{Introduction}

Manual food logging is difficult to sustain because it requires repeated identification, quantity estimation, database search, and entry correction. Image-based food recognition can reduce that effort by allowing a user to photograph a meal and receive detected food items. However, a visual label alone is not sufficient for dietary feedback. A user does not only need to know that an image contains \code{samosa}, \code{dal}, or \code{palak_paneer}; the label must be connected to calories, protein, carbohydrates, fat, and practical guidance.

Indian meals make this problem harder than ordinary object detection. A single plate may contain rice, curry, dal, chutney, fried bread, sweet dishes, and beverages. Dishes have regional variants and inconsistent names. The same food may appear as \code{WhiteRice}, \code{satham}, or \code{rice}; chutney labels may appear as \code{coconut_chutney}, \code{thengai_chutney}, or source-specific spellings; and visually similar dishes such as biryani and pulao may differ nutritionally by preparation and ingredients. This makes a direct detector-to-string-match approach fragile.

The core claim of this work is that nutrition-aware food recognition is a system problem rather than only a model problem. Object detection provides candidate labels and bounding boxes. A nutrition layer must then decide what each label means in a food-composition database. If that mapping is weak, the application can return precise-looking but wrong macro values. For example, \code{aloo_gobi} should resolve to potato cauliflower, and \code{palak_paneer} should resolve to spinach paneer. A fuzzy string match to a visually or linguistically adjacent but nutritionally different dish is not acceptable for a health-oriented interface.

This paper presents a working system and reports both model-level and pipeline-level validation. The contributions are:
\begin{itemize}
    \item a dataset engineering pipeline that merges five YOLO-format Indian food sources into a 72-class canonical dataset;
    \item a final YOLO11s detector evaluation on validation and held-out test splits;
    \item a conservative class-to-database mapping strategy for Indian nutrition lookup;
    \item a deterministic macro-target engine that adapts carbohydrate, protein, and fat targets to dietary goals and health profiles;
    \item a full-stack prototype that links food detection, nutrition retrieval, serving controls, daily macro tracking, and recommendation generation.
\end{itemize}

Unlike work that treats food recognition as a single-image classification task, this system is designed for multi-item meal images and user-facing nutrition feedback. Unlike direct vision-language nutrient estimation, the system does not ask a language model to invent calories or macro values. Nutrition values come from a structured database, while generated recommendations use already-computed backend values, user goals, and selected health conditions as input context.

The remainder of this article is organized as follows. Section II formalizes the problem. Section III reviews related work. Section IV describes the system architecture. Sections V and VI present the dataset pipeline and detector evaluation. Section VII explains nutrition database construction and mapping. The remaining sections describe the prototype, validation outcomes, ablation evidence, discussion, practical considerations, limitations, and conclusion.

\section{Problem Formulation}

\subsection{Notation and Objective}

Let $\set{X}$ denote the space of meal images and let $\set{C}=\{c_1,c_2,\ldots,c_K\}$ denote the canonical food-label vocabulary used by the detector. In this work $K=72$. A source dataset $s$ provides images $\set{X}^{(s)}$ and annotations $\set{A}^{(s)}$, where an annotation for image $x_i$ is a set
\begin{equation}
    A_i^{(s)}=\{(y_{ij}^{(s)},\vect{b}_{ij}^{(s)})\}_{j=1}^{n_i}.
\end{equation}
Here $y_{ij}^{(s)}$ is a source-specific class name and $\vect{b}_{ij}^{(s)}=(x_{ij},y_{ij},w_{ij},h_{ij})$ is a normalized bounding box. The dataset-engineering task is to learn or define a deterministic canonicalization function
\begin{equation}
    \phi_s: \set{Y}^{(s)} \rightarrow \set{C},
\end{equation}
where $\set{Y}^{(s)}$ is the raw label vocabulary for source $s$. The merged training corpus is therefore
\begin{equation}
    \set{D}=\bigcup_s \{(x_i,\{(\phi_s(y_{ij}^{(s)}),\vect{b}_{ij}^{(s)})\}_{j=1}^{n_i})\}.
\end{equation}

The detector is a parameterized function $f_\theta:\set{X}\rightarrow \set{P}$ that maps an image to a set of predictions
\begin{equation}
    f_\theta(x)=\{(\hat{c}_q,\hat{\vect{b}}_q,\hat{p}_q)\}_{q=1}^{Q_x},
\end{equation}
where $\hat{c}_q\in\set{C}$ is the predicted food class, $\hat{\vect{b}}_q$ is the predicted bounding box, $\hat{p}_q\in[0,1]$ is the confidence score, and $Q_x$ is the number of retained detections after non-maximum suppression.

Let the nutrition database be
\begin{equation}
    \set{N}=\{(n_\ell,\vect{m}_\ell,u_\ell,z_\ell)\}_{\ell=1}^{L},
\end{equation}
where $n_\ell$ is a food name, $\vect{m}_\ell=[e_\ell,p_\ell,h_\ell,g_\ell]^\top$ is a nutrition vector containing energy, protein, carbohydrate, and fat, $u_\ell$ is the serving basis, and $z_\ell$ is provenance metadata. The system requires a mapping operator
\begin{equation}
    M:\set{C}\rightarrow \set{N}\cup\{\emptyset\}
\end{equation}
that maps each detector class to a nutrition row or returns $\emptyset$ when no safe row exists.

For a detected meal image, the estimated nutrition vector is
\begin{equation}
    \hat{\vect{m}}(x,\vect{s})=\sum_{q=1}^{Q_x}\mathrm{I}[M(\hat{c}_q)\neq\emptyset]\,s_q\,\vect{m}_{M(\hat{c}_q)},
    \label{eq:meal_macro_vector}
\end{equation}
where $\vect{s}=[s_1,\ldots,s_{Q_x}]^\top$ contains user-adjusted serving multipliers. Equation~\eqref{eq:meal_macro_vector} is intentionally conservative: detections without mapped nutrition rows do not silently receive guessed nutrient values.

\subsection{System Risk Decomposition}

The end-to-end error in a nutrition-aware food-recognition system is not only detector error. It can be decomposed into at least four components:
\begin{equation}
    \set{E}_{sys}=\set{E}_{det}\cup\set{E}_{map}\cup\set{E}_{portion}\cup\set{E}_{rec},
\end{equation}
where $\set{E}_{det}$ is detection error, $\set{E}_{map}$ is class-to-database mapping error, $\set{E}_{portion}$ is serving or portion-size error, and $\set{E}_{rec}$ is recommendation-generation error. A detector with high mAP can still produce poor dietary feedback if $\set{E}_{map}$ is large. For example, a correct detection of \code{palak_paneer} still fails nutritionally if it maps to a generic paneer curry with substantially different spinach, oil, or cream composition.

This paper therefore defines the main objective as a constrained system problem:
\begin{equation}
    \max_{\theta,M} \quad \mathrm{mAP}(f_\theta;\set{D}_{test})+\lambda\,\mathrm{Cov}(M)
    \quad\text{s.t.}\quad
    \mathrm{Unsafe}(M)=0,
    \label{eq:objective}
\end{equation}
where $\mathrm{Cov}(M)$ is nutrition coverage over the canonical label set and $\mathrm{Unsafe}(M)$ counts mappings that are known to be semantically unsafe. The scalar $\lambda$ is not tuned in the prototype; it expresses the design priority that nutrition coverage must be achieved without accepting obviously wrong mappings.

\subsection{Research Questions}

The review manuscript is organized around four research questions:
\begin{itemize}
    \item RQ1: Can heterogeneous YOLO-format Indian food datasets be normalized into a single canonical label space without losing class coverage?
    \item RQ2: Does a YOLO11s detector trained on the canonical dataset generalize from validation to a held-out test split?
    \item RQ3: Does conservative class-to-database mapping provide complete nutrition coverage while avoiding unsafe fuzzy substitutions?
    \item RQ4: Does the full-stack prototype preserve auditability from image upload through detection, mapping, macro calculation, and recommendation generation?
\end{itemize}

\subsection{Matrix View of Mapping and Nutrition Aggregation}

The class-to-nutrition mapping can also be represented as a sparse assignment matrix
\begin{equation}
    \vect{A}\in\{0,1\}^{K\times L},
\end{equation}
where
\begin{equation}
    A_{k\ell}=
    \begin{cases}
    1, & \text{if canonical class } c_k \text{ maps to nutrition row } n_\ell,\\
    0, & \text{otherwise}.
    \end{cases}
\end{equation}
For a safe one-to-one mapping policy, each row of $\vect{A}$ has at most one nonzero entry:
\begin{equation}
    \sum_{\ell=1}^{L}A_{k\ell}\leq 1,\quad \forall k\in\{1,\ldots,K\}.
\end{equation}
Let $\vect{M}_N\in\mathrm{R}^{L\times 4}$ be the nutrition matrix where row $\ell$ is the macro vector for database row $n_\ell$. Let $\vect{z}\in\mathrm{R}^{K}$ be the detected class count or serving-weighted class vector for an image. The meal macro vector can then be written compactly as
\begin{equation}
    \hat{\vect{m}}=\vect{z}^{\top}\vect{A}\vect{M}_N.
    \label{eq:matrix_macro}
\end{equation}
Equation~\eqref{eq:matrix_macro} shows why the mapping matrix is central. Even if $\vect{z}$ is correct, incorrect nonzero entries in $\vect{A}$ produce incorrect macro totals.

\section{Related Work}

\subsection{Food Computing and Image-Based Dietary Assessment}

Food computing connects image analysis, recipe understanding, nutrition estimation, and dietary behavior \cite{min2019food}. Smartphone systems such as FoodCam demonstrated real-time mobile food recognition for dietary logging \cite{kawano2014foodcam}. Im2Calories framed the broader challenge of estimating food energy from meal images and showed that recognition alone is not enough when portion size and nutrient composition are uncertain \cite{meyers2015im2calories}. These works motivate the present system, but this paper focuses on regional Indian foods and the connection between detector labels and nutrition database rows.

\subsection{Detection Models for Multi-Item Meals}

Object detection is suitable for meal images because multiple food items can appear in the same photograph. Two-stage detectors such as Faster R-CNN separate region proposal and classification \cite{ren2015fasterrcnn}. YOLO-style one-stage detectors directly predict boxes and class probabilities, making them appropriate for interactive applications \cite{redmon2016yolo,redmon2018yolov3}. Recent Indian-food work has also moved toward multi-item detection and diet-logging workflows: IndianFoodNet compared YOLO-family detectors for Indian food items \cite{indianfoodnet_2023}, while dish-detection work on Indian platters reported large manually annotated platter datasets and evaluated several detection architectures for automated logging \cite{dish_platter_2023}. The implementation in this work uses Ultralytics YOLO11 tooling because it supports current YOLO training workflows, standard YOLO annotations, exported metrics, and Python integration \cite{ultralytics2024}.

\subsection{Dataset Bias and Regional Food Naming}

Datasets remain a central challenge. General object detection benchmarks such as COCO provide standardized object categories and annotations \cite{lin2014coco}. Regional food datasets are less uniform. They often use source-specific class names, inconsistent spelling, overlapping labels, and uneven annotation quality. Recent Indian cuisine benchmarks such as Khana show the scale and diversity of Indian food-image data, with classification, segmentation, and retrieval baselines over a broad Indian taxonomy \cite{khana_dataset_2025}. Thali-oriented research further shows why Indian meals need multi-component analysis rather than a single dominant food label \cite{indian_thali_2025}.

For nutrition-aware recognition, there is also a second mismatch: visual class names are short machine-learning labels, while food-composition databases contain descriptive recipe names, preparation details, and source metadata.

For Indian food recognition this mismatch is especially important because regional names often refer to the same preparation family. A rice dish can appear as \code{satham}, \code{WhiteRice}, or \code{rice}. A lentil dish can appear as \code{dal}, \code{daal}, \code{varan}, or a regional sambar-like preparation. A direct source-label union would therefore inflate the class count while fragmenting examples for the same dish. Conversely, aggressive merging can hide real nutritional differences, such as \code{chicken_biryani}, \code{mutton_biryani}, and \code{veg_briyani}. The present work treats label normalization as a controlled data-engineering step rather than as a purely automatic text-cleaning operation.

\subsection{Nutrition Databases and Recommendation Interfaces}

Nutrition lookup must therefore be treated as a first-class system component. Structured databases are preferable for calories and macro values because direct language-model nutrient estimates can appear fluent while being numerically unreliable. Recent work on Indian food-composition data and FKG.in emphasizes the need for structured Indian nutrition resources and explicit food-composition reasoning \cite{development_indb_2024,fkg_llm_2024}. At the same time, evaluations of LLM-based nutrient estimation from meal photographs report that visual identification and exact nutrient estimation remain different problems \cite{chatgpt_nutrient_estimation_2025}. This work therefore uses a local SQLite database derived primarily from Indian food-composition data, with source-backed supplemental rows only where the available database sheet lacks safe entries.

A review-ready food-assistance system also needs a clear separation between estimation and advice. The detector estimates visible food classes and bounding boxes. The nutrition layer retrieves database values. The macro engine transforms those values according to serving multipliers, user goals, and health profiles. The recommendation layer should receive computed values, not generate nutrient values directly. This separation is consistent with recent personalized diet-assistant work, where generated advice is most defensible when constrained by reliable nutrition inputs and user context \cite{nutrigen_2025,diet_engine_2025}. It also supports reviewer inspection because each source of error can be tested independently.

\subsection{Design Requirements}

The architecture is guided by six requirements. First, the detector must support multiple items per image because Indian meals commonly contain several visible dishes. Second, the nutrition lookup must be auditable; each macro value should be traceable to a database row and source. Third, the system must avoid unsafe automatic substitutions. Fourth, the application must expose enough information for user correction, especially serving-size adjustment. Fifth, macro targets must respond to dietary goals and health profiles. Sixth, the recommendation layer must not become the source of numeric nutrition values.

The image analysis endpoint validates uploaded files, runs inference, attaches nutrition records, and returns labels, confidence scores, bounding boxes, image dimensions, macro values, and source fields.

\subsection{Inference Data Contract}

The image-analysis endpoint returns a structured list of detections. For detection $q$, the backend response can be represented as
\begin{equation}
    d_q=(\hat{c}_q,\hat{p}_q,\hat{\vect{b}}_q,\eta_q,\vect{m}_q,z_q),
\end{equation}
where $\eta_q$ is the mapped database display name, $\vect{m}_q$ is the nutrition vector, and $z_q$ contains the nutrition source. If $M(\hat{c}_q)=\emptyset$, then $\eta_q$, $\vect{m}_q$, and $z_q$ are explicitly null and the response marks \code{nutrition\_not\_found}. This is a deliberate API-level guardrail. A frontend should not have to infer whether a calorie value was unavailable, estimated, or source-backed.

The macro total displayed to the user is computed from returned detections and serving multipliers:
\begin{equation}
    \vect{t}=\sum_{q=1}^{Q_x}s_q\vect{m}_q,
    \label{eq:macro_total}
\end{equation}
where $\vect{t}$ is the meal-level macro total. Equation~\eqref{eq:macro_total} separates recognition from portion adjustment: the detector decides what is visible, while the user-facing interface controls $s_q$ when the image alone cannot determine exact mass.

The frontend is implemented as a tool-first interface. It supports image upload, visual overlays, nutrition cards, serving adjustment, macro totals, and recommendation review. This design keeps the result inspectable: the user sees both the model output and the nutrition values attached to that output.

\subsection{Failure Modes Addressed by the Architecture}

The layered design addresses three common failure modes. The first is label drift, where a model class name changes but the backend lookup still expects an older label. Precomputed mappings reduce this risk by storing the accepted detector-to-database relation. The second is opaque nutrition generation, where a recommendation engine invents values that cannot be audited. The implemented flow prevents this by passing already-computed macros into recommendation prompts. The third is hidden missing data. When nutrition is unavailable, the backend returns an explicit missing state instead of forcing a low-confidence fallback into the response.

Each label row follows the normalized object detection format:
\begin{equation}
    r_i = (c_i, x_i, y_i, w_i, h_i),
\end{equation}
where $c_i$ is the class index and $(x_i,y_i,w_i,h_i)$ are normalized box coordinates. Source class indices are first decoded using each dataset's class list. Raw class names are then converted into canonical labels through lowercasing, punctuation normalization, synonym rules, regional-name handling, and manual mappings.

The canonicalization process applies the following ordered transformation:
\begin{equation}
    \phi_s(y)=\mu(\rho(\kappa(y))),
    \label{eq:canonicalization}
\end{equation}
where $\kappa(\cdot)$ performs case and punctuation normalization, $\rho(\cdot)$ applies regional-name and spelling rules, and $\mu(\cdot)$ applies the manually verified semantic mapping table. The order matters. String cleanup alone can align \code{AlooGobi} and \code{aloo\_gobi}, but it cannot safely decide whether \code{sambhar}, \code{sambar}, and \code{sambar\_satham} should become the same class. Those cases require semantic review.

This step is necessary because food-name variation is semantic, not cosmetic. Without canonicalization, the same dish can be split across several classes. That would reduce training examples per class, confuse evaluation, and later break nutrition lookup. Table~\ref{tab:normalization} gives examples.

\subsection{Split Construction}

The final dataset contains 72 canonical classes. The generated export contains 36,852 train image-label pairs, 5,922 validation pairs, and 5,919 held-out test pairs, for 48,693 total exported pairs. Training augmentation is applied only to the training split. Validation and test splits are kept as real held-out images so that detector evaluation is not inflated by transformed variants of training samples.

Let $\set{D}_c$ be the set of images containing class $c$. The split procedure aims to preserve class presence across train, validation, and test partitions:
\begin{equation}
    \set{D}=\set{D}_{train}\cup\set{D}_{val}\cup\set{D}_{test},
    \quad
    \set{D}_{train}\cap\set{D}_{val}\cap\set{D}_{test}=\emptyset.
\end{equation}
For each class $c$, the desired split proportions are approximately
\begin{equation}
    \left[
    \frac{|\set{D}_{train}\cap\set{D}_c|}{|\set{D}_c|},
    \frac{|\set{D}_{val}\cap\set{D}_c|}{|\set{D}_c|},
    \frac{|\set{D}_{test}\cap\set{D}_c|}{|\set{D}_c|}
    \right]
    \approx [0.70,0.15,0.15].
\end{equation}
Because an image can contain multiple food items, the split is a multi-label splitting problem rather than a simple class-balanced sampling problem.

\section{Detector Training and Evaluation}

\subsection{Detection Objective}

YOLO-style object detection optimizes localization, classification, and bounding-box distribution terms jointly. For a training batch $\set{B}$, the objective can be represented as
\begin{equation}
    \set{L}(\theta)=
    \lambda_{box}\set{L}_{box}(\theta;\set{B})+
    \lambda_{cls}\set{L}_{cls}(\theta;\set{B})+
    \lambda_{dfl}\set{L}_{dfl}(\theta;\set{B}),
    \label{eq:yolo_loss}
\end{equation}
where $\set{L}_{box}$ penalizes bounding-box localization error, $\set{L}_{cls}$ penalizes class prediction error, and $\set{L}_{dfl}$ is the distribution focal loss term used by the training implementation. The training configuration recorded in \code{args.yaml} uses $\lambda_{box}=7.5$, $\lambda_{cls}=0.5$, and $\lambda_{dfl}=1.5$.

For a predicted box $\hat{\vect{b}}$ and ground-truth box $\vect{b}$, intersection-over-union is
\begin{equation}
    \mathrm{IoU}(\hat{\vect{b}},\vect{b})=
    \frac{\mathrm{area}(\hat{\vect{b}}\cap\vect{b})}
    {\mathrm{area}(\hat{\vect{b}}\cup\vect{b})}.
\end{equation}
Predictions are counted as true positives when the predicted class is correct and the IoU exceeds the evaluation threshold. Precision and recall are then
\begin{equation}
    P=\frac{TP}{TP+FP},\qquad R=\frac{TP}{TP+FN}.
\end{equation}
Average precision for a class is the area under its precision-recall curve:
\begin{equation}
    AP_c=\int_0^1 P_c(R)\,dR.
\end{equation}
The reported mAP@50 is the mean AP over classes at IoU threshold 0.50, while mAP@50:95 averages AP over thresholds from 0.50 to 0.95.

\section{Nutrition Database and Mapping}

\subsection{Database Construction}

The nutrition database is built by importing an INDB spreadsheet into SQLite, following the project requirement for Indian food-composition coverage \cite{development_indb_2024}. The build script validates required columns, normalizes food names, converts nutrient values to numeric form, removes duplicate normalized names, and creates a read-optimized table for backend lookup. The final database contains 1,010 food records.

Each database row is represented as
\begin{equation}
    n_\ell=(\mathrm{name}_\ell,\mathrm{norm}_\ell,\mathrm{kcal}_\ell,
    \mathrm{protein}_\ell,\mathrm{carb}_\ell,\mathrm{fat}_\ell,
    \mathrm{source}_\ell,\mathrm{url}_\ell).
\end{equation}
The normalized name is indexed because most lookups compare the normalized detector label against normalized database names. Complete macro fields are required before a row is retained; rows with missing calories, protein, carbohydrate, or fat values are excluded from the database import.

\subsection{Mapping Policy}

The mapping layer converts a detector class into a nutrition database row. The decision rule is conservative:
\begin{equation}
\resizebox{0.98\columnwidth}{!}{$
M(c)=
\begin{cases}
M_{\mathrm{manual}}(c), & \text{if verified manually},\\
M_{\mathrm{exact}}(c), & \text{if normalized names match},\\
M_{\mathrm{sup}}(c), & \text{if a supplemental row exists},\\
M_{\mathrm{fuzzy}}(c), & \text{if score}(c) \geq \tau,\\
\emptyset, & \text{otherwise}.
\end{cases}
$}
\end{equation}
Here $\tau=0.78$ is the fuzzy-match threshold used by the database builder. The empty case is intentional. In nutrition-aware applications, missing nutrition data is preferable to a confident but wrong macro estimate.

Let $\psi(\cdot)$ be the food-name normalizer and let $\sigma(a,b)$ denote the fuzzy similarity score between strings $a$ and $b$. The fuzzy fallback can be written as
\begin{equation}
    M_{\mathrm{fuzzy}}(c)=
    \argmax_{n_\ell\in\set{N}}\sigma(\psi(c),\psi(n_\ell)).
\end{equation}
The candidate is accepted only when the maximum score is at least $\tau$. Manual mappings override this fallback because the highest string score is not always the safest nutrition match. For example, a regional spelling variant may have a low string score but a clear semantic target, while a visually related dish may have a high string score but a different macro profile.

Table~\ref{tab:mappings} shows representative mappings. Exact and manual mappings receive high confidence. Approximate mappings, such as \code{ven_pongal} to plain khitchdi, are recorded with lower scores so they remain inspectable.

\begin{equation}

\subsection{Macro Target Engine}

The deterministic macro engine converts a user goal and daily calorie target into carbohydrate, protein, and fat gram targets. Let
\begin{equation}
    \vect{g}=[g_c,g_p,g_f]^\top
\end{equation}
be the base macro percentage vector for a dietary goal, where $g_c$, $g_p$, and $g_f$ are carbohydrate, protein, and fat percentages. Let
\begin{equation}
    \vect{r}=[r_c,r_p,r_f]^\top
\end{equation}
be the health-condition modifier vector. The adjusted macro percentages are computed by normalized elementwise scaling:
\begin{equation}
    \tilde{\vect{g}}=
    100\cdot
    \frac{\vect{g}\odot\vect{r}}
    {\vect{1}^\top(\vect{g}\odot\vect{r})},
    \label{eq:macro_modifier}
\end{equation}
where $\odot$ denotes elementwise multiplication. Given a calorie target $E$, the gram targets are
\begin{equation}
    T_c=\frac{E\tilde{g}_c}{400},\qquad
    T_p=\frac{E\tilde{g}_p}{400},\qquad
    T_f=\frac{E\tilde{g}_f}{900}.
    \label{eq:macro_targets}
\end{equation}
The denominators encode 4 kcal/g for carbohydrate, 4 kcal/g for protein, and 9 kcal/g for fat.

\subsection{Recommendation Generation Guardrail}

The recommendation prompt is constructed from detected foods, database-backed macro values, the user goal, and the health-condition descriptor. Let $\set{F}_x$ be the set of food records returned from the backend for image $x$. The prompt context is
\begin{equation}
    \set{Q}=(\set{F}_x,\vect{t},\tilde{\vect{g}},E,h),
\end{equation}
where $\vect{t}$ is the meal macro total, $\tilde{\vect{g}}$ is the adjusted macro percentage vector, $E$ is the target calorie budget, and $h$ is the health-condition key. The language model receives $\set{Q}$ and generates advice text, but the numeric macro vector remains fixed by the deterministic backend calculations. This design avoids treating generated text as a measurement instrument and allows the deterministic macro calculation to be tested independently of the external recommendation provider.

\section{Ablation and Benchmark Evidence}

\subsection{Why Detector Metrics Alone Are Insufficient}

The final detector metrics establish that the model can localize and classify Indian food items with usable accuracy. They do not prove that the application returns correct nutrition feedback. For a detection $q$, the user-visible macro vector depends on both the detector and the mapping:
\begin{equation}
    \vect{m}_q = \vect{m}_{M(\hat{c}_q)}.
\end{equation}
If $\hat{c}_q$ is correct but $M(\hat{c}_q)$ is wrong, then the nutrition result is wrong. If $\hat{c}_q$ is wrong but maps to a plausible-looking food row, the frontend can display a confident but incorrect macro card. The system must therefore be evaluated at multiple levels.

\section{Discussion}

The results support the central design decision: the detector and nutrition layer must be evaluated together. The final YOLO11s detector provides usable object detection performance on the expanded 72-class dataset. However, detector output becomes useful to a diet application only after labels are mapped to reliable food-composition rows. A wrong mapping can turn a correct visual detection into misleading nutrition feedback.

The conservative mapping strategy reduces this risk. Manual semantic mappings handle cases where strings differ but meanings match. Supplemental rows cover classes absent from the available INDB sheet while preserving source provenance. Fuzzy matching is retained only as a fallback rather than the primary source of truth. This is especially important for Indian foods because regional names, spelling variants, and preparation-family substitutes can look close in text while differing meaningfully in macronutrients.

The implemented full-stack workflow also changes the interpretation of the result. The project is not only a detector benchmark; it is a traceable image-to-recommendation pipeline. The frontend exposes labels, boxes, confidence scores, macro cards, serving controls, remaining daily macro values, and recommendation text. This makes incorrect detections and uncertain serving assumptions easier to notice than in a black-box calorie-estimation interface.

The system also shows the value of simple validation artifacts. Contact sheets found annotation problems that file counts would miss. Runtime lookup tests caught mapping behavior that detector mAP would not measure. API and frontend workflow checks caught data-contract issues that model evaluation would not expose. This suggests that nutrition-aware food recognition should report model metrics, nutrition provenance, and application-level validation together.

\section{Ethical and Practical Considerations}

The prototype is intended for dietary logging assistance and nutrition awareness, not for diagnosis, treatment, or clinical decision-making. The system displays nutrition values from database rows and uses generated text only after backend macro values have already been calculated. This separation reduces the risk that a language model will invent calories, protein, carbohydrates, or fat values.

Image-based food analysis can involve privacy-sensitive user data if deployed beyond a local prototype. A production deployment should therefore provide explicit consent, retention limits, secure storage, and a clear deletion path for uploaded meal images and analysis records. If the system is used with health profiles such as diabetes, hypertension, kidney disease, anemia, or thyroid disorder, recommendations should remain conservative and should direct users to qualified professionals for medical decisions. The interface should also communicate low model confidence, supplemental nutrition sources, and approximate mappings instead of presenting all values as equally certain.

\section{Limitations}

The system has five important limitations. First, nutrition values are reported per database serving basis and do not estimate exact food mass from the image. Accurate portion estimation would require depth cues, reference objects, segmentation masks, calibrated serving assumptions, or learned volume estimation. Second, five nutrition records are supplemental because the available INDB sheet does not contain safe rows for every detector class. Third, some mapped rows are documented substitutes rather than exact dish-level records. Fourth, the detector has uneven per-class behavior, especially for visually similar dishes and classes with fewer unique examples. Fifth, visual verification was sample based; it found obvious issues but does not guarantee that every annotation is correct.

The recommendation layer is also not clinically validated. Although macro arithmetic is deterministic and testable, natural-language advice depends on provider behavior when an external language model is configured. The prototype should therefore be interpreted as a decision-support system rather than a clinical nutrition instrument. It can reduce logging effort and provide useful macro context, but it should not be presented as medical advice.

\section{Future Work}

Future work should address five directions. First, a self-trained or rule-constrained recommendation model should replace the external language-model dependency for applications that need consistent, auditable advice. Second, portion-size estimation should be added through reference objects, depth estimation, segmentation masks, or calibrated plate assumptions. Third, model benchmarking should be extended to same-split YOLO-family baselines and augmentation ablations. Fourth, mobile deployment should be evaluated because food logging is naturally camera-first. Fifth, longitudinal tracking should be added through user accounts, meal history, trend charts, and manual correction tools, while maintaining privacy controls and medical-safety boundaries.

\section{Conclusion}

This paper presented AI-based food recognition with nutrition-aware recommendations for Indian meals. The system joins YOLO11s detection, canonical dataset engineering, conservative class-to-database mapping, structured nutrition lookup, deterministic macro calculation, health-profile-aware targets, and a full-stack web prototype. The dataset pipeline produced 48,693 image-label pairs across 72 classes. The final YOLO11s model achieved 0.820 mAP@50 and 0.680 mAP@50:95 on the held-out test split. The nutrition layer produced 1,010 food records and mapped all 72 expanded classes to safe nutrition entries. The full-stack prototype demonstrates how detection, bounding boxes, macros, serving adjustment, daily tracking, and recommendations can be connected in a practical Indian food assistant. The main lesson is that credible food recognition requires not only accurate visual models, but also auditable label normalization, nutrition provenance, conservative handling of uncertain mappings, and a clear boundary between computed nutrition values and generated dietary advice.
