\begin{abstract}
Food-recognition applications are useful only when the predicted food label is connected to reliable nutrition information. This paper presents an AI-based Indian food recognition system that detects visible food items, links them to nutrition records, calculates macronutrients, and generates nutrition-aware recommendations from the computed values. The main technical contribution is a conservative nutrition-grounding layer placed between the YOLO detector and the recommendation module. Instead of relying on direct fuzzy string matching, the layer uses canonical class names, explicit semantic mappings, source-backed supplemental rows, thresholded fallback matching, and provenance metadata. Five YOLO-format Indian-food datasets were merged into a 72-class dataset with 48,693 exported image-label pairs. A YOLO11s detector trained on this dataset achieved 0.820 mAP@50 and 0.680 mAP@50:95 on the held-out test split. The nutrition database contains 1,010 food records and 103 detector-to-database mappings, covering all 72 expanded classes. Macro verification reported 51 verified mappings, 21 review-level mappings, and zero failed mappings. The resulting prototype connects image upload, detection overlays, nutrition lookup, serving adjustment, and personalized recommendations while keeping the numerical nutrition layer separate from generated advice.
\end{abstract}

\begin{IEEEkeywords}
food recognition, nutrition-aware recommendations, YOLO, Indian food dataset, dietary assessment, macronutrients

\section{Introduction}

Most food-recognition systems stop at the visual task: they identify what appears in an image. A diet-assistance application has to go one step further. A detected class such as \code{palak_paneer}, \code{rice}, or \code{samosa} must be linked to a nutrition entry before the system can say anything useful about calories, protein, carbohydrates, or fat. If this link is wrong, the final recommendation may look precise while being nutritionally misleading.

This problem is especially visible in Indian meals. The same dish can appear under different spellings, regional names, or dataset-specific labels. For example, plain rice may be listed as \code{WhiteRice}, \code{satham}, or \code{rice}. A chutney label may refer to the side dish itself or to a small portion beside a larger food item. Biryani and pulao classes may look similar in an image but differ in ingredients and macro values. These cases make direct string matching a weak basis for nutrition lookup.

This paper presents a project titled \textit{AI-Based Food Recognition with Nutrition-Aware Recommendations}. The system uses YOLO11s for object detection, a curated Indian-food dataset, a SQLite nutrition database, and a recommendation layer that receives already-computed nutrition values. The key idea is to keep recognition, nutrition grounding, and recommendation generation separate. The detector predicts visible food items; the nutrition layer decides whether a safe database match exists; the recommendation module uses those values to produce diet-aware guidance.

The contributions are:
\begin{enumerate}
    \item a 72-class Indian-food object-detection dataset built by merging and normalizing five YOLO-format datasets;
    \item a conservative detector-to-nutrition mapping method that reduces unsafe nutrition substitutions;
    \item a working FastAPI and Next.js prototype that connects detection, macro calculation, serving adjustment, and personalized recommendations.
\end{enumerate}

\section{Related Work}

The literature reviewed for this project falls into three groups: Indian food recognition, nutrition database alignment, and recommendation systems. Work outside this scope, especially 3D volume or depth-based portion estimation, is not central to this paper because the implemented system reports database-backed per-100g macro values and leaves portion adjustment to the user.

Indian food recognition work shows why a domain-specific detector is needed. IndianFoodNet uses YOLO-style detection for Indian food items, which is closer to real meal images than single-label classification because one plate may contain several dishes \cite{indianfoodnet_2023}. Khana presents a larger Indian cuisine classification benchmark and highlights the familiar problems of class imbalance, visual similarity, and regional variation \cite{khana_dataset_2025}. The Indian Thali study goes further toward cluttered meal analysis through segmentation and controlled capture, but that setup is less convenient for a normal web-upload workflow \cite{indian_thali_2025}. Lightweight CNN and MobileNetV3 studies also support the use of compact models and train-time augmentation, though they remain closer to classification than multi-item detection \cite{lightweight_cnn_food_2022,mobilenetv3_indian_food_2023}.

The nutrition side of the literature is equally important. The Indian Food Composition Database work explains why cooked Indian recipes need dedicated nutrient records rather than direct raw-ingredient assumptions \cite{development_indb_2024}. The Synergistic Frameworks study directly identifies the compatibility problem between visual food labels and nutrition databases: the detector may use one label, while the nutrition row uses a different spelling, language, or preparation name \cite{synergistic_frameworks_2025}. FKG.in shows how language models and food knowledge graphs can help parse regional recipe descriptions, but the present system begins from a photograph rather than a typed recipe \cite{fkg_llm_2024}. This is why the implemented backend uses deterministic database lookup and audited class-to-food mappings instead of asking a language model to invent nutrition values.

Recent recommendation systems show the value and the risk of generative AI in diet applications. NutriGen and other web-based meal-planning systems use LLMs to generate personalized plans from structured user constraints \cite{nutrigen_2025,genai_meal_planning_2025}. Diet Engine combines food detection with NLP-based dietary guidance, which is close to the high-level direction of this project \cite{diet_engine_2025}. At the same time, evaluations of ChatGPT-style nutrient estimation from meal photographs warn that fluent responses do not guarantee accurate calorie or macro values \cite{chatgpt_nutrient_estimation_2025}. The design used here follows that lesson: the recommendation layer receives detected foods and calculated macros from the backend, while nutrition arithmetic remains database-backed and inspectable.

\section{Proposed System}

Fig.~\ref{fig:pipeline} summarizes the implemented system. The pipeline starts with dataset normalization and model training. At runtime, the frontend sends an uploaded food image to the backend. The backend runs YOLO11s, resolves each predicted class through the nutrition mapping table, calculates macro values, and returns the structured result to the frontend. Recommendation text is generated only after the numeric nutrition values have been calculated.

Let a detector return
\begin{equation}
D_x=\{(\hat{c}_q,b_q,p_q)\}_{q=1}^{Q_x},
\end{equation}
where $\hat{c}_q$ is the predicted food class, $b_q$ is the bounding box, and $p_q$ is the confidence score. Let the nutrition database be
\begin{equation}
N=\{(n_j,\mathbf{m}_j,z_j)\}_{j=1}^{L},
\end{equation}
where $n_j$ is a food name, $\mathbf{m}_j=[e_j, protein_j, carb_j, fat_j]$ is the nutrition vector, and $z_j$ stores source metadata.

The mapping function $M$ resolves a detector class to a nutrition row:
\begin{equation}
\resizebox{0.98\columnwidth}{!}{$
M(c)=
\begin{cases}
M_{\mathrm{manual}}(c), & \text{if a reviewed semantic match exists},\\
M_{\mathrm{exact}}(c), & \text{if normalized names match},\\
M_{\mathrm{sup}}(c), & \text{if a verified supplemental row exists},\\
M_{\mathrm{fuzzy}}(c), & \text{if score}(c,n)\geq0.78,\\
\emptyset, & \text{otherwise}.
\end{cases}
$}
\label{eq:mapping}
\end{equation}
The final case is important. If no safe nutrition match exists, the system keeps the detection but does not invent macro values. In a health-oriented interface, a missing value is preferable to a wrong confident value.

For a meal image, the displayed macro vector is
\begin{equation}
\hat{\mathbf{m}}(x)=\sum_{q=1}^{Q_x}s_q\mathbf{m}_{M(\hat{c}_q)},
\end{equation}
where $s_q$ is the serving multiplier selected by the user. This keeps portion adjustment explicit rather than pretending that exact food weight can be recovered from a single image.

\subsection{Runtime Data Contract}

The backend response is designed so that the frontend does not need to infer the meaning of missing or approximate values. Each detection carries the raw detector label, display name, confidence score, bounding box, image dimensions, macro values, nutrition unit, nutrition source, and missing-nutrition flag. If no valid food is detected, the API returns an explicit no-food state. If a class is detected but no safe nutrition match exists, the detection remains visible while macro values are left unavailable. This choice makes the system easier to inspect and prevents a recommendation from being based on hidden guesses.

\section{Dataset Construction}

Five YOLO-format Indian-food datasets were merged into one canonical dataset \cite{roboflow_placeholder}. Source class names were decoded from each dataset configuration file, normalized for case and punctuation, and then reviewed for semantic variants. Examples include mapping \code{AlooGobi}, \code{aloo gobhi}, and \code{aloo_gobi} to \code{aloo_gobi}; mapping \code{WhiteRice}, \code{satham}, and \code{rice} to \code{rice}; and mapping \code{medu vadai} to \code{medu_vada}. Multi-food label files were preserved by rewriting every valid YOLO annotation row.

The merge process used a 70/15/15 target ratio for training, validation, and test splits. Multi-label images were retained because a realistic food photograph may contain several dishes. Augmentation was applied only to the training split, mainly for underrepresented classes, so that validation and test metrics were not inflated by synthetic variants of the same images.

A visual verification script sampled real images for every class and generated contact sheets. This check confirmed that all 72 classes have image samples. It also found three local annotation issues: one \code{jalebi} sample that did not visually match jalebi, one \code{kaara_chutney} box placed on a vada, and one extremely thin \code{nandu_masala} box. These issues were recorded for future cleanup and did not indicate a class-order error.

\section{Detector Training and Evaluation}
\suppressfloats[t]

The final detector was trained with YOLO11s at 640-pixel image size and batch size 16. Training resumed from epoch 56 and continued to epoch 100 on a Tesla T4 GPU. The best logged validation mAP@50 was 0.83379 at epoch 78. On the held-out test split, the exported model reached 0.842 precision, 0.801 recall, 0.820 mAP@50, and 0.680 mAP@50:95 across 5,919 images and 8,875 instances.

The recommendation module uses the detected foods, calculated calories, macro totals, user goal, calorie target, and health profile. It does not generate the calorie and macronutrient values itself. This separation keeps the advice layer from becoming a source of fabricated numeric nutrition data.

The macro engine converts a calorie target into carbohydrate, protein, and fat grams. A selected goal defines the base macro split, and a health profile modifies that split before normalization. For a calorie target $T$ and final macro percentages $p_c$, $p_p$, and $p_f$, the target grams are:
\begin{align}
G_c &= \frac{T p_c}{4 \times 100}, &
G_p &= \frac{T p_p}{4 \times 100}, &
G_f &= \frac{T p_f}{9 \times 100}.
\end{align}
The recommendation service receives these calculated values along with detected foods. For example, a high-carbohydrate fried meal under a weight-loss goal can trigger portion-control and protein-pairing advice, while a diabetic profile can shift the emphasis toward carbohydrate moderation and fiber.

\suppressfloats[t]

Dataset checks confirmed that class folders, label files, split counts, and visual samples were present. Model evaluation measured detection performance on validation and held-out test splits. Nutrition checks verified that detector classes resolve to complete macro rows. This layered validation is useful for peer review because each failure mode is different. A detector can classify a food correctly while the nutrition service maps it poorly. A nutrition database can be complete while the frontend receives fields under unexpected names. Treating these checks separately makes the system easier to debug and makes the reported results more transparent.

\section{Discussion}

The project shows that the most fragile part of a nutrition-aware food assistant is often not the detector itself. A visually correct prediction can still become a poor dietary result if it is mapped to the wrong food-composition row. This is why the mapping table, source metadata, and explicit missing-value behavior are treated as part of the AI pipeline rather than as backend convenience code.

The system also shows a practical trade-off. It does not attempt exact portion estimation from a single image, because that would require assumptions that are difficult to verify in ordinary user photographs. Instead, it reports database-backed macro values and lets the user adjust serving multipliers. This is less ambitious than automatic plate-weight estimation, but it is more defensible for a working prototype.

\section{Limitations}

The system does not estimate exact portion mass from the image. Nutrition values are reported from database rows and adjusted through user-selected serving multipliers. Better portion estimation would need segmentation, depth cues, reference objects, or calibrated serving-size assumptions. The detector also has uneven per-class behavior for visually similar foods and classes with fewer diverse samples. Finally, the 21 review mappings should be interpreted as practical approximations rather than exact recipe equivalence.

\section{Conclusion}

This paper presented \textit{AI-Based Food Recognition with Nutrition-Aware Recommendations}, an end-to-end system for Indian food detection, nutrition lookup, macro calculation, and personalized dietary guidance. The project combines a YOLO11s detector, a 72-class canonical Indian-food dataset, a conservative nutrition-mapping layer, and a full-stack prototype. The detector achieved 0.820 mAP@50 on the held-out test split, while the nutrition layer mapped all 72 expanded classes with zero failed macro mappings. The main lesson from the project is straightforward: food recognition becomes useful for dietary support only when visual predictions are grounded in auditable nutrition data and passed to the recommendation layer with their uncertainty preserved.
